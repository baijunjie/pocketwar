# 开发笔记

记录从代码和提交历史里读不出来的东西：需求的来龙去脉、试过又放弃的路、踩过的坑、还没验证的事。
玩法、操作、目录结构见 [README](../README.md)，这里不重复。

## 需求与取舍的来历

- **原始需求**：同屏上千单位的即时战略，浏览器运行；四个阵营（中国、日本、罗马、波斯）各有特点；
  不建造不发展，像「突袭」系列那样直接给一整支部队；单机；大地图，有地形、城池、营地，建筑全部可破坏；
  占领资源点后定时从后方来援军。
- **原创作品**：名称「烽烟」。不照搬任何现有游戏的名称、美术、文明设计或具体外观。
- **画面走过的三步**，每一步都是用户看过之后否掉上一步：
  1. 2D 俯视贴图 —— 「怎么是纸片人」，要全 3D。
  2. 3D + CC0 卡通素材包（Kenney Mini Characters / Castle Kit / Survival Kit、KayKit Medieval Hexagon）——
     「不要 Q 版，要写实」。这些包已从仓库移除。
  3. 现状：人物、器械、战象、建筑、树石全部由代码按真人比例建模，只有马用 CC0 模型。
- **为什么不用现成的写实模型**：调研过 Kenney、KayKit、Quaternius、poly.pizza、OpenGameArt，
  没有找到 CC0、带骨骼动画、写实精度的古代士兵；也没有 CC0 的中 / 日 / 罗马 / 波斯风格建筑包，
  没有可直接用的 CC0 带行走动画的大象。Quaternius 的成人比例人物包是候选，但官方 Google Drive 当时限流下不动。
  用户最后说「没有的话你就自己做」。以后如果用户自己提供或购买模型，`rig.ts` 的烘焙流程可以直接接 glTF 骨骼模型
  （马就是这么接的）。
- **写实程度的上限**：现在是低多边形、纯色顶点色、无贴图。离商业 3D 即时战略的精度有差距，用户知情。
- **阵营平衡按用户意思暂停**：「先不用关注平衡，我要先看效果」。用户发话前不要再调数值。
  停手前的数据：36 局 AI 对战胜场为日本 14/18、中国 8/18、波斯 8/18、罗马 6/18；
  那之后还改过一次参数，整局胜率没有重测。平衡工具在测试里：
  `VITE_BALANCE=duel npx vitest run -t 对冲`（平地对冲）、
  `VITE_BALANCE=1 VITE_ROUND0=<轮次> npx vitest run -t 打完整局`（整局）。

- **第二轮需求（架构与玩法）**：用户要求把「固定算法」和「可替换内容」解耦、模型素材可换、兵种可扩展，
  并加入体型、等级、行军 / 战斗状态、特殊动作、士气溃逃、昼夜天气、粮草，随后又追加了城邦 / 营寨、
  火把烧建筑、城墙驻守、新的占领规则。规则与数值记在 [gameplay.md](gameplay.md)。
  这一轮新机制必然改变了阵营强弱，**没有重新做平衡**，兵种原有的数值一个没动。
- **这一轮里自行定的、用户没逐条确认过的规则**（用户有异议就改）：
  - 石城门可以被火把慢慢烧开（×0.3）。用户原话只说「城墙不能被人形单位破坏」；如果城门也烧不动，
    没有器械的一方就永远进不了敌方城邦。
  - 战象算工程类（能破城墙），不是人形单位。
  - 摧毁据点主建筑后据点变成无主废墟、可被任何一方重新占领并修复（原先是永久失效）。
  - 「逃向距离我方最近的地图边缘」按「离这个溃兵最近的边缘」实现。
  - 玩家可以按 T 熄灭火把；溃兵不算守军。
  - 石墙对己方是「到处都能上」，没有做楼梯；寻路时给上墙加了代价，所以行军仍走城门。

## 协作约定

- 下载任何第三方文件（含 npm 包）之前，先向用户说明文件名、来源、授权、大小并得到明确同意。
  只用 CC0 或同等宽松授权的素材，来源记在 README 的「素材」一节。
- 用户用简体中文交流，喜欢简短直接的回答；尽早给能看的版本，而不是全部做完才展示。
- 提交用 Conventional Commits、中文、不留 AI 痕迹；在分支 + `.worktrees/<名字>` 工作树里开发，
  交付前压成一个提交，快进合并到 main。

## 模拟层与渲染层的边界

- `src/sim/` 是纯逻辑，可在 Node 里无头运行，**世界是平的**：丘陵、山只是地形类型。
  高度只存在于渲染层（`terrain.ts` 的高度场），单位脚下高度由 `Renderer.groundY` 现算。
- 坐标对应：模拟的 `(x, y)` → three.js 的 `(x, z)`，`y` 轴朝上。单位是世界像素，每格 32，士兵按每米 10 像素建模。
- 为 3D 在模拟层只加了一样东西：`World.dir`（朝向角，`atan2(dy, dx)`，每秒最多转 9 弧度）和尸体的 `cDir`。
  原有的 `facing`（±1）仍在，模拟自己还在用。
- **内容与系统**：`content/` 是数据表，`systems/` 是算法，`World` 只存状态并按 `world.systems` 这条管线逐个调用。
  想换一套规则就替换管线里的一项；想加兵种、调数值只动 `content/`。系统之间不互相调用状态以外的东西，
  例外是 `units.ts` 会调 `combat` / `targeting` / `morale` 里的函数（它是最热的循环，拆成多遍会慢）。
- **常量放在 `sim/state.ts`**，不要放回 `world.ts`：`world.ts` 引用各系统，各系统又要用这些常量，
  放在一起会形成循环引用——Node 里的测试碰巧能过，浏览器里按另一种顺序加载就报
  `Cannot access 'NONE' before initialization`。系统文件里对 `world.ts` 只做 `import type`。
- 渲染层读的新状态：`World.state`（`S_COMBAT / S_CHARGE / S_BRACE / S_SHIELD / S_TORCH / S_ROUT / S_WALL`）、
  `level`、`maxHp`、`seen`（被哪一队看见）、`env`（天光、雨势）。敌军画不画看 `seen`，不是看所在格是否可见——
  远处打着火把的敌人所在的格子可以是暗的。
- `World.fx / fxN` 是特效事件队列，**渲染层每帧消费后必须把 `fxN` 清零**，否则会溢出。
- `atkAnim` 在出手那一刻被设为 0.3 再按秒递减，所以攻击动画是「命中之后」播放的 0.3 秒：
  动作要设计成一开始就快速出手、后面慢慢收势，否则伤害跳出来时手还没挥。
- `odo` 是累计行进距离（像素）。步伐动画的相位 = `odo ÷ 步幅`，步幅由模型给出（`UnitModel.strides`，
  动作名 → 一个循环前进多少像素：步兵走 15、跑 28.4，马走 21、跑 35）。改动作的步子大小时改步幅，不用动模拟层。
  走还是跑由渲染层按实际速度判断（超过行军速度的 1.14 倍算跑）。
- 桥：模拟里是可通行的 `T_BRIDGE` 格，渲染里那一格的地形是河床，`groundY` 对桥格直接返回桥面高度。

## 渲染上踩过的坑

- **上千单位怎么画**：每个兵种把所有动画帧的骨骼矩阵烘进一张浮点贴图（一行一帧，一根骨骼 4 个纹素），
  几何体带骨骼编号，实例属性只给「位置 + 朝向 + 第几行」。不要逐个单位做蒙皮，也不要每单位一个 Mesh。
- **性能是这样调回来的**：约 2000 单位同屏时最初只有 38 FPS，三项改动后回到 60：
  几何体合并顶点改成索引绘制；每顶点骨骼数从 4 降到 2；镜头拉远（距离 > 2400）时单位不再投影。
  人物用不封口的圆管做肢体省面。马是面数大户（约 2200 面，骑兵合计近 3000 面），再要提速先从马下手。
- **`Puppet.pose` 复位时必须跳过根节点**。早先连根节点一起复位，调用方给模型设的缩放和朝向被清掉，
  表现为「马缩成一小团」「模型朝向不对」，很难联想到是这里。
- **马的模型**：glTF 里骨架和网格节点各带一个 100 倍缩放，直接读包围盒不可信，
  要用 `skinnedBox`（按骨骼矩阵算）来量再缩放。动画有带 `AnimalArmature|` 前缀的重复项，取不带前缀的。
- **骑手的座位**：取马的 `Torso` 与 `Torso3` 两根骨骼之间 0.6 处，每帧跟随。只取 `Torso` 会坐到马屁股上。
- **贴地标记（选中圈、占领圈）**：要画在地形之上、单位之下。做法是材质 `transparent: false` + 自定义混合，
  让它留在不透明队列里，再用 `renderOrder` 紧跟地形绘制并关掉深度测试。
  放进透明队列的话会在所有单位之后才画，圈就盖到人身上了。
- **战争迷雾**：不是后处理，是一张小贴图（64 像素一格）在每个材质的片元着色器末尾压暗。
  新增材质要走 `materials.ts` 的 `litMaterial`，否则迷雾里它会是亮的。
  未探索区域只压暗、不抹黑：地形是已知的，看不到的是敌军和建筑。
- **建筑**：按「模型种类」分组成 `InstancedMesh`，只有当某栋建筑的存活 / 归属 / 血量档 / 受击闪白 / 是否已探索
  变化时才重写实例缓冲（`syncBuildings` 里的签名比较）。归属色只体现在旗帜上，建筑本体不随归属换色。
- **头像**：`portrait.ts` 用一个独立的离屏渲染器现渲，必须在素材（马）加载完之后才能调用，
  所以 `main.ts` 先 `loadAssets()` 再进菜单。
- three.js 固定在 0.170；着色器补丁依赖它的 `#include <begin_vertex>` 等片段名，升级后要重新核对。

- **换模型的入口**：兵种 → 模型 id（`UnitDef.model`，缺省等于兵种 key）→ `models/catalog.ts` 里的说明 →
  `models/spec.ts` 的 `buildUnitModel`。渲染器只认标准动作名（idle / walk / run / attack / die，
  可选 attackMove / charge / brace / guard / guardWalk），缺的按 `CLIP_FALLBACK` 回退。
  要预加载的素材清单由登记表自动得出（`modelAssets()`），不用另外维护。
- **夜晚和下雨没有用后处理**：只调了太阳光、天空光的强度与颜色和雾色（`Renderer.applyEnvironment`）。
  打火把的单位靠实例的「明暗」分量提亮，再加一个火苗和一圈贴地的暖光，并没有真的光源。
- **城墙上的单位**靠渲染层把高度抬到 `BuildingDef.top`，上下墙有一段平滑过渡（`Renderer.lift`）；
  模拟里世界仍然是平的。墙的模型厚度（`buildings.ts` 里的 `T`）要和「能站人」的观感对得上。

## 调试手段

- 直达参数：`/?f=china&e=japan&size=600&seed=42&fog=0&spectate=1`。开发模式下 `window.game` 是当前对局
  （`game.world`、`game.renderer.cam`、`game.renderer.three.info.render` 等都能直接读写）。
- 模型预览页：`/?view=units`，`&k=legion` 只看一个兵种，`&clip=move` 固定播放某个动作；`window.viewer` 里有相机和控制器。
  调模型、动作先在这里看，比进对局快得多。
- 想马上看到大规模交战：在控制台把两军的坐标搬到同一处、各下一道攻击移动、再把 AI 的 `update` 换成空函数。
  注意开打后减员很快，测帧率要在头十几秒内取数。
- 量帧率用 `requestAnimationFrame` 数 3–4 秒的帧数，不要看界面左上角那个平滑过的读数。
- 想看夜晚 / 下雨：控制台里 `R = (await import('/src/sim/content/rules.ts')).RULES`，
  改 `R.env.startClock` 可以拨时刻（时刻 = startClock + 已过秒数 ÷ 480，取小数部分；0.9 是深夜），
  `game.world.env.nextWeather = game.world.time` 立刻切换晴雨。
- 单位「原地打转」的度量在 `tests/helpers.ts` 的 `spinStats`：没在交手的单位每秒转过的角度和白跑的路程。
  注意用血量无限的靶子时，靶子会被人群推着走，围着它的人跟着漂，这部分也会算进「白跑」。
- 测试计时受机器负载影响很大（并行跑别的任务时慢 3～4 倍），比性能要和旧代码背靠背跑。

## 已验证与未验证（截至首个里程碑）

已在浏览器里实测：镜头平移 / 缩放；框选、右键移动、攻击移动、编队、小地图点击跳转；战争迷雾；据点占领；
约 1800–2060 单位同屏混战 60 FPS（窗口 1625×913，被刷新率封顶）。`npm test` 10 项通过，`npm run build` 通过。

  （镜头旋转只通过直接改参数看过）。

- 成队行军时脚下是否还打滑；完整的一局人机对战。

## 第二轮（架构与玩法）的验证情况

已验证：`npm test` 33 项通过（新增 23 项，覆盖体型与速度、默认队列、编队行军、战斗状态、冲锋、立枪、举盾、
经验升级、溃逃与重整、逃散、昼夜视野、火把、下雨、粮草、寻敌、火把烧木栅、石墙免疫、驻守城墙、占领读秒与修复）；
`npm run build` 通过；两整局 AI 对战（300 人）分别在 30 分钟和 19 分钟分出胜负，途中有溃逃、占领、修复发生。
浏览器里实际看过：预览页的行军、冲锋、立枪、举盾动作；glTF 通用流程（用马试的）；对局里的溃兵发白、等级金点、
夜晚火把、下雨、弩兵上墙、火把烧木栅、旗帜圈与界面上的粮草 / 士气 / 时辰。

「原地打转」的前后对比（没在交手的单位平均每秒白跑的像素，旧 → 新）：攻击移动的骑兵 22.6 → 约 6，
待命部队贴近敌军 35 → 约 20，攻击移动的步兵 1.9 → 约 5（略有回升，因为会横向去找有空位的敌人）。
待命那一项的残余主要来自上面说的靶子漂移。

性能：3000 单位混战的单帧模拟耗时约为原来的 1.7 倍（同一负载下背靠背 3.2ms → 5.3ms，预算 12ms），
主要花在更大的警戒范围扫描和两队各算一遍视野上。

没有验证过：

- 阵营平衡（见上）。也没有跑过 36 局那样的整局胜率统计。
- 粮草在真人对局里的松紧：两局 AI 对战里双方都没断过粮（AI 扩张很快），断粮只在测试里人为触发过。
- 等级的节奏：两局里绝大多数单位停在新兵和老兵，精锐以上极少，阈值可能偏高。
- 真人操作下的整局体验、T 键熄火把的手感、攻打敌方城邦（烧城门 / 砸城墙）在 3D 下的全过程。
- 举盾、立枪、冲锋只在预览页逐个看过姿势，没有在对局的近景里盯着确认触发时机。
- 用真正的士兵 glTF 模型换装（手头没有 CC0 的，只拿马走通了流程）。

## 第三轮（操作、队列与城防的反馈）

用户试玩后提的 12 条，实现时定下的做法和踩到的坑：

- **城墙分内外**：寻路层加了两张表，`nav.deck[队伍]`（本队能站上去的墙顶 / 楼顶）和 `nav.inner`（城墙圈内的地面，
  开局由 `world.sealWalls()` 按各据点带 `top` 的建筑的包围盒圈出来）。墙顶与地面之间只有另一头是 `inner` 才能走，
  这条规则要同时写进三处，否则会对不上：流场搜索（`nav.step`）、单位位移的碰撞（`systems/units.ts`）、
  `world.lineBlocked`（决定走直线还是用流场）。自己搭世界的测试如果要上墙，记得调 `sealWalls()`。
- 石墙两格厚是在地图上铺两圈 1×1 的墙格，不是把墙的占地改成 2×2；门楼、角楼是 2×2，正好嵌进去。
  墙的模型按格生成，垛口只砌在「隔壁既不是墙也不是城内」的那几条边上，所以渲染层要读 `nav.inner`。
- **贴地标记被模型盖住**：贴地层（`Quads` 的 ground）不做深度测试、紧跟地形画，后画的桥和城墙会把它盖掉。
  桥面、墙顶上的圆环和落点改走另一层 `raised`（做深度测试 + 深度偏移），由 `Renderer.flat()` 按脚下是不是
  桥 / 建筑来分流。地面上不能也走这一层：坡地上会被地形切掉一半。
- **点在墙顶上**：`screenToWorld` 原来只和地形求交，点墙顶得到的是墙后面的地面。现在落地之前沿视线回看一段，
  先碰到墙顶就算在墙上（点在外墙立面上也会算到墙顶，没有再细分）。
- **站定出手**：`w.planted[]` 记每个单位这一帧是否站定（1 = 非骑兵在交手或出手，2 = 骑兵在交手、或在战线后列队等待）。
  站定的人不吃浅的推挤；别人撞上站定的人，自己全让。调这个的时候试过、放弃的几条路：
  - 把没站定的人的推挤上限从 3 提到 6：人堆里抖得更厉害。现在的做法是上限只比自己一帧能走的距离多 0.5，
    刚好够抵消「跑得快的一点点挤进人堆」。
  - 把朝向站定者的那部分速度直接削掉（只留贴着滑过去的分量）：穿不进去了，但后排永远绕不到空位，交手的人数掉到三成。
  - 「换目标」的条件原来是「比现在的目标人少就换」，敌人挤不动之后会在两个都围满的敌人之间来回跑；
    改成对方确实有空位才换。追击的「卡住」也改成看有没有朝目标靠近，横着滑不算。
  交手者 15 秒内的位移：步兵约 0.5～1.7 像素，骑兵约 6 像素（`tests/systems.test.ts` 里有断言）。
- **编队行军**（`systems/march.ts`）：领队走流场，成员跟位置；位置够不着（`lineBlocked`）时成员回落到原来的
  「各自走流场」，所以过桥时队形会散、过去之后重组，没有做成纵队变换。电脑指挥官每隔几秒会对同一队人重复下
  同一道命令，`orderMove` 里认出来就沿用现有编队，否则每次都要回重心重新整队。
- 镜头旋转其实第一版就有（Q / E、Alt + 中键），只是没人找得到：这一轮改成中键直接拖就是旋转，并写进了帮助。
- 边缘卷屏的鼠标位置要在 `window` 上跟踪，只听画布的话鼠标停在小地图、按钮面板上就卷不动。

这一轮的验证：`npm test` 39 项通过（新增 6 项：城墙内外与角楼、防御建筑放箭与可烧毁、休整与修复、编队行军与朝向、
站定出手、溃兵防御）；`npm run build` 通过。浏览器里实际看过：两格厚的城墙与正反面、弩兵从城内上墙再走上角楼、
点墙顶的落点与令旗、墙顶和桥面上的选中圆环、右键拖动的朝向箭头与到位后的队列、行军途中的队列、溃兵头顶的白旗、
边缘卷屏（离边 30 像素与 3 像素的速度约 1 : 3）。

两整局 AI 对战（600 人，中国对日本、罗马对波斯）分别在 17.7 和 21.2 分钟分出胜负，途中有占领（24 / 40 次）、溃逃、
门楼与角楼被毁；两局都是 1 队大胜（剩 900 对 10 余人），滚雪球明显，平衡仍未调。

没有验证过：真实鼠标的右键拖动和中键旋转（右键拖动是用脚本派发指针事件试的）、Shift+数字追加编队的真实按键、
门楼 / 角楼放箭和被烧毁在画面上的样子（只有测试）、据点内回血与建筑自修在对局里的观感、
过桥和进城门时队列散开再重组的观感、大规模混战里「站定」之后战线推进是否显得太慢。

## 第四轮（溃兵恢复、音效、单兵面板、攻击移动打建筑）

- **音效**（`src/audio/sound.ts`）全部现场合成，没有用任何音频文件，所以也不涉及素材授权。战斗声读的是模拟层的
  特效事件 `world.fx`，而渲染器每帧画完会把它清零——所以 `sound.update()` 必须排在 `renderer.render()` 前面。
  为了给「放箭」出声，模拟层加了一个只用来出声的事件 `FX_SHOT`（渲染器不认识它，直接跳过）。
  同一种声音在几十毫秒内只响一次，期间的事件合并成一声（越多越响），以离镜头最近的那一下定音量和声像。
  我听不到声音：只确认了 AudioContext 在运行、各种事件确实触发了合成调用、控制台没有报错，**音色和音量都没有人耳听过**。
- **攻击移动不打城门**是上一轮编队行军带进来的：成员跟着队列位置走，绕过了原来「行军路线被建筑挡住就地攻打」的那段逻辑，
  领队自己又被门挡住不动，全队就站在门口。现在领队被建筑挡住时置 `blocked`，成员回落到各自走流场的旧逻辑。
- 途中自己盯上的建筑（箭楼、门楼）原来是「继续沿行军路线走，走到够得着再打」，不在路线旁边的就永远打不着；
  现在能直线走到就直接上前。
- 溃兵恢复：士气系统原来整个跳过溃兵，现在照常算，过了「阈值 + recover」就恢复。副作用是脱离接触的溃兵几秒后就会自己稳住，
  真正一路逃回据点的只剩士气被长期压着的情况；相关测试用「把士气钉在 0」来模拟后者。
- 等级阈值从 0 / 40 / 110 / 240 / 480 降到 0 / 30 / 80 / 160 / 300：用户反馈对局里最多只见到 3 级。

这一轮的验证：`npm test` 41 项通过（新增 2 项：攻击移动打开营门并烧门楼、溃兵在友军身边恢复）。浏览器里看过单兵详情面板。
没有验证过：音效的听感；新阈值下整局的等级分布；溃兵半路恢复在对局里的观感。

## 第五轮（资源点、升级、雪天、据点火把）

用户一次提了八条：雪天；据点夜里自动升火把；四种资源点（占领后自动采集）；黄金升级兵种的高级形态（外观明显多披甲）；
石料升级城邦、木材升级营寨（外观要变，易主降回，有料时修得快）；木材给资源点建箭塔（最多 4 座，位置固定）、
部队在野外搭临时据点；塔楼有视野加成。规则与数值记在 [gameplay.md](gameplay.md)。

**这一轮自行定的、用户没逐条确认过的**（有异议就改）：

- 用户原话里「城镇」指城邦（大本营、城池、城镇，花石料），「据点」指营寨（营地、村庄、马场、工坊，花木材）。
  大本营也能升级。
- 「屏幕上所有单位」按字面做：「全部升级」的范围是**镜头里看得见的**己方单位 / 据点，不是全图。
- 黄金产量随开局兵力走（0.8U / 分钟），木材、石料是固定数量：升级全军的花费随兵力涨，升级据点的花费不随兵力变。
- 资源点开局全是中立、没有箭塔；资源点不算据点（不能休整、不计士气、雪天没有遮蔽），临时据点算。
- 升级后原本不放箭的主建筑会添一队弓手——否则村庄、马场、工坊这类不设防的营寨「升级后攻击力上升」无从谈起。
- 临时据点不能占领、只能摧毁；每方最多 3 座；木材下令时扣、搭不成退还。
- 雪天不扣士气（用户没提）；「据点之外防御下降」做成护甲减半。
- 据点的火把只是画面，不改规则；雨雪天也照点。中立据点也点。
- 挨了箭塔的箭会上去拆塔（待命的不超过离岗 330）。原来箭塔的箭没有「来源」，待命在塔下的部队只会干挨打；
  没有这一条，站在资源点旗下的部队会被箭塔一个个射死而不还手。这也让靠近敌方城邦待命的部队会去烧门楼、角楼。
- 电脑会花资源（升级部队、升级据点、建箭塔），不会扎营，也不会专门去拆玩家的临时据点。

**实现上值得记的**：

- **高级形态是独立的兵种定义**（`key_e`，紧跟在原兵种后面，`UnitDef.elite / basic / tier` 互相指）。升级就是改
  `w.type[i]`。这样渲染层不用动：它本来就是每个兵种一批、一个模型。代价是 `UNITS` 翻了一倍，遍历 `UNITS`
  做界面（比如菜单的兵种表）时要注意只取 `tier === 0`——菜单是按 `factions.ts` 的编制取的，所以没受影响。
- 高级形态的模型在 `catalog.ts` 末尾按阵营的重甲样式自动推出来（`heavyLook`），`HumanLook` 新增的
  `plate / vambrace / cuisse / greaves / aventail` 给了颜色就加上对应的甲片。新甲片都并进原有肢体的那一次
  `addRigid` 里，没有多占骨骼列。马的全身马甲是按骨骼名把更多部位刷成甲色（`bardingFull`），马的骨骼名见
  `horse.glb`：Body / Torso / Neck / Head / Front·BackShoulder / UpperLeg / LowerLeg / Tail / Ear。
- 两队共 56 个兵种模型全部在开局烘焙，实测进对局的时间没有可感的变化，所以没有做成按需烘焙。
- **资源点和临时据点都是 `Site`**，靠 `SiteInfo` 上的数据开关区分（`reinf: null` 不出援军、`haven` 能否落脚、
  `counts` 计不计士气、`captureTime: 0` 不能占领、`towerSlots`）。系统里不要再写 `type !== SITE_HQ` 这种判断。
  临时据点是对局中途 `world.addSite()` 加出来的，被毁后置 `gone`（`sites` 按下标取，不能删），遍历据点的地方要跳过 `gone`。
- **建筑的生命上限是 `b.maxHp`，火力是 `b.tower`**，不要再读 `b.def.hp` / `b.def.tower`：据点升级后两者都变了。
  `w.armed` 只增不减，放不放箭看 `b.tower` 是否为空。
- **渲染器的建筑分组改成了动态的**：原来开局按模型种类建好 `InstancedMesh` 和固定的成员表，现在每次有变化时
  先数一遍每种模型要画几个、容量不够就换一个更大的，再逐个写入。升级（模型换成 `:1` 那一份）、中途新建的箭塔与行营、
  倒塌与重建都走这一条路。墙的四邻掩码仍然只在登记时算一次（`registerBuildings`）。
  地形只在开局给建筑脚下铲平，中途新建的直接坐在地表上，坡地上会略微悬空或陷进去。
- **积雪**：`shared.uSnow`（0..1）。地形着色器里把地表色往白里混（路面、夯土白得慢）；`litMaterial` 里按法线朝上的程度
  把建筑、树石的顶面刷白（片元里用 `vNormal` 点乘观察空间的上方向）。单位不积雪。
  雪花是固定在世界里的一片雪花场（位置由序号哈希出来、按视野范围取模），不能像雨丝那样每帧随机撒，会闪。
- 据点的火把最初插在塔顶正中，升级后被箭亭的屋顶整个挡住；改成插在垛口四角、主建筑门前。
- 选中据点：`game.ts` 的 `siteAt()`——点在据点的建筑上，或点在旗帜圈（85）里。点空地原来是取消选择，现在多了这一步，
  所以在据点里点空地会选中据点（按 Esc 或选部队即取消）。
- 用鼠标点右上角的调速按钮后鼠标停在屏幕边缘，镜头会一直往上卷——用脚本测试时别忘了把鼠标挪回中间。

这一轮的验证：`npm test` 57 项通过（新增 `tests/economy.test.ts` 16 项：高级形态的数值、升级次序与花费、资源点的数量与箭塔位、
占领与采集、箭塔挡占领与重建、挨箭还击、塔楼视野、据点升级与易主降回、有料修得快、临时据点的搭建 / 上限 / 退款、
雪天的速度 / 视野 / 火把 / 护甲、电脑会花资源）；`npm run build` 通过。3000 单位混战的单帧模拟耗时与改动前背靠背没有差别（6.5～7.2ms）。
两整局 AI 对战（600 人）在 19.9、18.9 分钟分出胜负，胜方把全军和十二三个据点都升了级；那两局里电脑一座箭塔也没建
（木材总是先被营寨升级花光），改成「建塔、升级轮流」之后同样的对局建了 11 座。
整局里偶尔有 40～100ms 的慢帧，在改动前的版本上跑同一脚本同样有（散落在各个系统里，不是这一轮引入的）。

浏览器里实际看过：预览页里 28 个兵种初级、高级形态并排对比；对局里的资源点模型（伐木场、采石场、金矿、农庄）、
顶栏的木 / 石 / 金、据点列表里的资源点小牌子；点旗帜选中资源点、点「建箭塔」三次（箭塔出现、黄圈减少）；
框选部队后点「升级所选部队」（222 人换成重甲模型，卡片换名）；点「城邦全部升级」后的大本营外观与名牌的星；
升级后的营地；夜里大本营与营地的火把；雪天的积雪与雪花；按 B 再点地面扎营（部队赶到后行营落成、扣木材）。

没有验证过：

- 阵营平衡与经济的松紧——数值都是第一版：金矿产量、升级花费、高级形态与据点升级的加成都没有调过。
  两局 AI 对战里胜方后期黄金大量富余（全军升完后攒到七八千）。
- 真人对局里敌军来抢有箭塔的资源点、拆临时据点、据点易主降级的全过程（只有测试）。
- 「部队全部升级」「营寨全部升级」两个按钮没有实际点过（和点过的那两个走同一段代码）；Esc 取消选中据点、
  从右侧列表点选据点没有实际点过。
- 雪夜（雪与夜晚叠加）的画面、雪停后化雪的过渡；下雪是直接改状态触发的，没有等到自然下雪。
- 电脑建的箭塔、电脑升级后的据点在画面上的样子；升级后的城池、城镇、村庄、马场、工坊各自的外观只看了大本营和营地。
- 新增的界面在小窗口（高度不足 700）下会不会互相遮挡。

## 已知的遗留

- 没有重新做阵营平衡；编队行军后，带着器械的部队整体很慢（这是需求本身，嫌慢就分开下令）。
- AI 是全知的：它不受战争迷雾和夜晚影响来做战略判断（单位层面的索敌受视野限制）。AI 也不会主动熄火把或夜袭。
- 城墙没有楼梯：己方单位从城内一侧的任何位置都能上下，城外一侧上不去。门楼顶上不能站人。
- 编队行军过桥、进城门时队形会散开，过去之后重组；散得太开的部队（均方根距离 > 520）不编队。
- 站定出手之后，被己方战线挡在后面的近战单位只能等空位，不会主动绕到侧翼。
- 人形单位在行军路线上被石墙挡住时不会绕路找城门，会停下；有器械同行则等器械开路。

- 经济数值没有调过；黄金除了升级部队没有别的去处，全军升完后会一直富余。
- 电脑不会扎营，也不会主动去拆玩家的临时据点（攻击移动只会顺手打会放箭的建筑，行营不放箭）。
- 中途新建的建筑（箭塔、行营）脚下的地形没有铲平。临时据点可以贴着山脚、林子搭。
- 升级、建造没有专门的音效（只有下令的提示音）。
- 待命的单位被箭塔射中后直线上前，中间隔着别的建筑时会被挡住、放弃、再挨箭再上前，来回几次。
- 音效没有人耳校过；没有脚步声、呐喊和背景音乐。
- 桥不可破坏，也没有栏杆（桥常是斜着跨河，栏杆方向会错）。
- 大部队绕河找渡口时会沿岸拉成长队。
- 单位在坡上不会随坡度倾斜；下摆、披风、旗帜是刚性的，不会飘动。
- 披甲的马只是把躯干换成甲色，没有单独的马甲模型。
