# 验证、测量与测试

- 量帧率用 `requestAnimationFrame` 数 3～4 秒内的帧数，不读界面左上角的 FPS（指数平滑过，反应慢）。
  要马上看大规模交战：开发模式下控制台的 `window.game` 是当前对局，把两军坐标搬到同一处、各下一道攻击移动，
  再把电脑指挥官（`game.game.ais` 里每一个）的 `update` 换成空函数；开打后减员很快，帧率要在头十几秒内取数。
- 比性能（帧率、单帧模拟耗时、测试计时）要和改动前的代码在同一负载下背靠背跑：机器上并行跑着别的任务时计时会慢 3～4 倍。
  `tests/sim.test.ts` 里「单帧模拟耗时在预算内」在全量并行跑时偶尔超预算，先单独重跑、再和改动前背靠背比，才能判断是不是改动引入的。
- 比单帧模拟耗时的快慢，用打包后的代码测（如用 vite 自带的 `esbuild` 把同一份测量脚本分别对改动前后的代码打包，再用 node 跑），
  不拿 vitest / vite-node 里的计时下结论：那里每次读 import 进来的绑定（如 `RULES`）都要过一层 getter，热循环的开销被放大，
  改动前后的快慢比也跟着失真（实测过一份在 vite-node 下慢约 3 倍的改动，打包后只慢约 2 倍）。
- 复现、量化模拟层行为（走位、队形、交战）用无头脚本：脚本放仓库外的临时目录，用仓库里的 `node_modules/.bin/vite-node --root / <脚本绝对路径>` 跑，
  脚本以绝对路径 import 某个工作树的 `src/sim/...` 与 `tests/helpers.ts`。不加 `--root /` 时 vite 拒绝加载项目根目录外的文件（报 `Cannot find module '/@fs/…'`）。
  同一份脚本换个根路径，就能在改动前（主分支所在工作树）与改动后背靠背跑，仓库里不留临时文件。
  真实地图用 `src/sim/setup.ts` 的 `createGame`（关掉 `fog`、`spectate`、`environment`、`supply` 少些干扰），空旷平地用 `tests/helpers.ts` 的 `flatWorld`；
  推进用同文件的 `run`，自己写循环时每帧 `w.tick()` 后要 `w.fxN = 0`（特效缓冲平时由渲染层清空）。
  改动前后的对比、交给别人复测或定成测试门槛，都以同一脚本前后对照为准，转述数字时连口径（数谁、采样哪一段、隔几帧采一次）一起给：同一指标换个口径，绝对值能差两三倍。
- 队形、走位类问题要出俯视图看形状：把单位坐标、不可通行格、行迹画成 PNG（Node 自带的 `zlib.deflateSync` 就能手写最小 PNG 编码，不必装依赖）。
  只看数字看不出折叠、压进墙里这类形状问题；看清形状后再配一个对应它的标量（如队首到队尾的直线距离 ÷ 纵深）做多种子对比。
- 用脚本驱动浏览器时，点完靠近屏幕边缘的按钮（如右上角调速）要把鼠标挪回屏幕中间，否则鼠标停在边缘带里会一直卷屏。
- 动态效果（平滑跟随、抖动、弯曲的弹道）静态截图看不出：逐帧读数值（如每帧镜头位移）或录动图来确认；没确认的，交付时说明。
- 音效改动无法亲耳确认：能核对的只有 AudioContext 在运行、事件确实触发了合成、增益值合理、控制台无报错；交付时明说音色和音量未经人耳确认，请用户试听。
